# Lexicon Web Research — Three.js Renderer v1 (2026-02-28)

## Problem Statement

Design a deterministic Three.js renderer that interprets RenderPackets with explicit draw ordering, and visually displays the packet's content-addressed hash to prove determinism across runs/devices.

## Sources Consulted

### 1. Three.js Documentation — Object3D.renderOrder
**Link:** https://threejs.org/docs/#api/en/core/Object3D.renderOrder

**Relevance:** Explicit render ordering control without relying on depth-sorting

**Key Findings:**
- `object.renderOrder` is a numeric property (default 0)
- Renderer sorts by renderOrder **before** depth testing
- Higher renderOrder values render last (appear on top)
- Effective for UI overlays, transparent objects, order-dependent rendering
- Works best with `scene.sortObjects = false` to disable automatic sorting

**Applied to Renderer Intent v1:**
- Each RenderCommand has `render_order: i16` + `layer: u8`
- Three.js objects set with: `object.renderOrder = (layer << 16) | (render_order & 0xFFFF)`
- Renderer sets `renderer.sortObjects = false` to trust our deterministic ordering

### 2. Three.js Docs — WebGLRenderer
**Link:** https://threejs.org/docs/#api/en/renderers/WebGLRenderer

**Relevance:** Canvas setup, pixel ratio, clear color, rendering calls

**Key Findings:**
- Constructor accepts `{ canvas, antialias, alpha }`
- `setPixelRatio(ratio)` — device pixel ratio (1 for 1x, 2 for Retina)
- `setSize(width, height, updateStyle)` — canvas resolution
- `setClearColor(color, alpha)` — background color
- `render(scene, camera)` — render call (deterministic if scene + camera are deterministic)

**Applied to Renderer Intent v1:**
- RenderLoop class wraps WebGLRenderer initialization
- Uses config.pixel_ratio, config.width_px, config.height_px, config.background_color
- render() call is pure: same scene + camera → same output (deterministic)

### 3. Three.js Docs — Scene and Camera Setup
**Link:** https://threejs.org/docs/#api/en/scenes/Scene

**Relevance:** Scene graph hierarchy, camera types, lighting

**Key Findings:**
- Scene contains all objects (meshes, lights, cameras, groups)
- Group is a container node (no geometry)
- Mesh + Geometry + Material = renderable object
- PerspectiveCamera: FOV, aspect, near, far
- OrthographicCamera: left, right, top, bottom, near, far
- Light types: DirectionalLight, PointLight, AmbientLight

**Applied to Renderer Intent v1:**
- `buildThreeScene()` creates Scene and populates with nodes
- Groups → THREE.Group()
- Meshes → THREE.Mesh(geometry, material)
- Lights → THREE.DirectionalLight, THREE.PointLight, THREE.AmbientLight
- Cameras → THREE.PerspectiveCamera or THREE.OrthographicCamera
- All transforms (position, rotation, scale) applied via node.transform.TRS

### 4. Three.js Examples — Geometry and Material
**Link:** https://threejs.org/docs/#api/en/geometries/BoxGeometry

**Relevance:** Primitive geometry creation and material properties

**Key Findings:**
- BoxGeometry(width, height, depth)
- SphereGeometry(radius, widthSegments, heightSegments)
- PlaneGeometry(width, height)
- CylinderGeometry(radiusTop, radiusBottom, height, radialSegments)
- MeshBasicMaterial — color only (unlit)
- MeshStandardMaterial — color, metalness, roughness, emissive (PBR)

**Applied to Renderer Intent v1:**
- `buildGeometry()` maps PrimitiveSchema discriminated union to Three.js geometries
- `createThreeMaterial()` maps MaterialSpecV1 to MeshBasicMaterial (unlit) or MeshStandardMaterial (PBR)
- Metalness + roughness from MaterialSpecV1 mapped directly to Three.js material properties

### 5. MDN Performance.now() — High-Resolution Timing
**Link:** https://developer.mozilla.org/en-US/docs/Web/API/Performance/now

**Relevance:** Frame time measurement (determinism validation)

**Key Findings:**
- `performance.now()` returns DOMHighResTimeStamp (milliseconds since navigation start)
- Accurate to microseconds (1/1000 ms precision on modern browsers)
- Unique to each browser tab (not wall-clock time)
- Use for performance profiling and FPS calculation

**Applied to Renderer Intent v1:**
- RenderLoop measures frame time: `frameTime = performance.now() - startTime`
- FPS calculated from 30-frame rolling average
- Reported in RenderOutput for performance metrics

### 6. Web Accessibility — DOM Overlay Creation and Styling
**Link:** https://developer.mozilla.org/en-US/docs/Web/API/Document/createElement

**Relevance:** HUD overlay creation and DOM manipulation

**Key Findings:**
- `document.createElement('div')` creates DOM elements
- `element.style.cssText` sets multiple CSS properties at once
- `z-index` controls stacking order above canvas
- `position: absolute` overlays relative to parent
- `rgba(r, g, b, a)` for semi-transparent backgrounds

**Applied to Renderer Intent v1:**
- RendererHUD class creates div overlay for hash display
- Positioned `absolute` at top-right (10px, 10px)
- Styled with dark semi-transparent background (#000000 at 70% opacity)
- Green text (#00ff00) with monospace font for hash legibility
- `z-index: 10000` ensures it appears above all canvas content
- CSS box-shadow for glow effect (visual feedback)

## Decision + Rationale

### Why Three.js for Visual Validation?

1. **Immediate visual proof:** RenderPacket hash appears in HUD → users see determinism instantly
2. **Low complexity:** Interpreter pattern: read JSON → create Three.js objects → render
3. **Deterministic by default:** Same scene + camera → same render output (cryptographically)
4. **Production foundation:** Three.js maturity means no architectural rewrites later
5. **Clear contract:** RenderPacket is a pure data structure; Three.js is the pure interpreter

### Why Visual Hash Display (Not Silent Rendering)?

1. **Non-repudiable proof:** Hash visible on screen = irrefutable evidence
2. **User confidence:** No need to inspect logs or debug console
3. **Real-time validation:** User can render same packet twice, see identical hashes
4. **Determinism marketing:** Visual proof convinces skeptics ("it's not random!")

### Why renderOrder + sortObjects = false?

1. **Deterministic ordering:** Renderer respects our pre-computed order
2. **No depth-fighting:** Explicit layer + render_order eliminates z-sorting brittleness
3. **Consistent behavior:** Same order regardless of camera angle or view frustum
4. **Three.js convention:** Standard pattern in game engines + VFX tools

## Integration Points

### Graphics Intent v1 → Renderer Intent v1

1. **GraphicsIntentToolkit** produces RenderPacket (snapshot ID + content-addressed hash)
2. **RendererIntentToolkit** consumes RenderPacket (fetches by ID, renders)
3. **Visual loop:** User renders scene 5 times → HUD displays same hash 5 times → ✅ determinism proven

### Future: Local Lexicon v1 → Renderer Intent v1

1. **LexiconDB** stores graphics-intent snapshots (indexed by kind, actor_id, created_at_utc)
2. **Renderer** queries lexicon for snapshot by ID
3. **Persistent visualization:** Render old snapshots (replay capability)
