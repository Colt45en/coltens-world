# docs/lexicon/web/nexus-world-build/2026-02-27.md

## Problem statement
Design the best contract-first, deterministic, local-first build process for a World Engine "Nexus Build" spanning: local lexicon, avatar/building prefabs, 3D mesh style rules, chat engine, physics stepping, graphics intent/render substrate, world environment (snapshot/replay), and automation. The process must prioritize reproducibility, auditability, replay, and clean module boundaries compatible with a Nucleus tool_call lane.

## Findings (actionable)
Canonical JSON + hashing:
- RFC 8785 provides a concrete, implementation-ready model for creating a stable, hashable JSON representation using deterministic property sorting and constrained JSON forms suitable for cryptographic hashing.

Fixed timestep simulation:
- "Fix Your Timestep!" demonstrates why variable dt causes unstable behavior and why accumulating time and stepping simulation at fixed dt is a robust baseline for physics and replayable simulation.

Physics determinism in JS:
- Rapier's WASM/TS/JS docs state the JS/WASM build is cross-platform deterministic when using the same Rapier version, same initial conditions, and deterministic upstream computations. The docs also warn that platform math like Math.sin/Math.cos may not be cross-platform deterministic, meaning simulation inputs must be produced deterministically to preserve engine determinism.

3D asset pipeline:
- Khronos positions glTF as a runtime asset delivery format ("JPEG of 3D"), with .glb as a single-file packaging method. This is a strong fit for a prefab pipeline that wants stable distribution and consistent PBR representation.

Local lexicon storage determinism:
- SQLite distinguishes deterministic vs non-deterministic functions and highlights time-dependent behavior (e.g., date/time "now" usage) as a determinism hazard. SQLite PRAGMAs can affect compilation vs execution and have compatibility cautions; therefore any PRAGMA reliance must be explicitly versioned and documented in build metadata.

## Decision + rationale
Decision: Use a "substrate-first, contracts-first" build process:
1) Substrate: RFC 8785-style canonical JSON + sha256 hashing + append-only ledger + content-addressed artifact store.
2) Contracts: Define schemas for lexicon, prefab, mesh style, chat, physics, graphics intent, world snapshot/replay, automation.
3) Spine order: Mesh Style → Prefab + Baker → World Snapshot/Replay → Physics Stepper (fixed dt) → Graphics Intent → Chat Stream → Lexicon Local Store → Automation.

Rationale:
- Mesh style first prevents asset chaos and reduces rework.
- Prefabs provide composition units used by world, physics, and graphics.
- Snapshot/replay early guarantees every later subsystem is testable and auditable.
- Fixed timestep is a proven baseline for stable physics and replay.
- Rapier JS/WASM determinism provides a pragmatic path for cross-platform stable simulation, while still requiring deterministic input generation.
- Canonical JSON per RFC 8785 makes hashing reliable for ledger and artifacts.

## Notes on determinism hazards to bake into contracts
- Any list ordering must be contract-defined (sorted vs preserved).
- Any timestamps must be treated as metadata, not functional output, unless explicitly provided as input.
- Physics inputs must avoid non-deterministic math sources (platform trig); quantize or centralize deterministic math if cross-platform replay is required.
- SQLite usage must avoid nondeterministic SQL behaviors; always specify ordering and avoid time-dependent functions unless explicitly parameterized.
