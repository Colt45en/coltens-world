# Lexicon Web Research — Graphics Intent v1 (2026-02-28)

## Problem Statement

Design a deterministic, content-addressed representation of a 3D scene + materials + viewport that can be hashed and replayed identically across runs/devices, and interpreted by a renderer (e.g., Three.js).

## Sources Consulted

### 1. Khronos glTF 2.0 Specification (Oct 11, 2021)
**Link:** https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html

**Relevance:** Scene graph structure (nodes, scenes, children hierarchies)

**Key Findings:**
- glTF organizes geometry into a **node hierarchy** with parent-child relationships
- Nodes can be groups (no geometry) or meshes (with primitive references)
- Each node has a **TRS (translate, rotate, scale) matrix** in row-major order
- Materials define appearance (texture references, color, metallic, roughness)
- Scenes are collections of nodes with explicit root node references

**Applied To Graphics Intent v1:**
- `NodeSpecV1` mirrors glTF node structure (node_id, children array, transform TRS)
- `SceneSpecV1` mirrors glTF scene (root_nodes array, nodes array)
- `MaterialSpecV1` captures PBR material properties (base_color, metallic, roughness, emissive)

---

### 2. glTF 2.0 Reference Guide PDF (circa 2022)
**Link:** https://www.khronos.org/files/gltf20-reference-guide.pdf

**Relevance:** Readable overview of scenes/nodes/materials arrays and their ordering semantics

**Key Findings:**
- Nodes are stored in a flat array; hierarchy is maintained via **children array indices**
- Scenes contain an array of root node indices; order in this array is **NOT semantically meaningful** but should be preserved for reproducibility
- Materials array is indexed; order is **NOT semantically meaningful** but affects serialization

**Applied To Graphics Intent v1:**
- Scene nodes stored as flat array with explicit node_ids for reference
- Root nodes array is sorted to ensure deterministic order independent of insertion
- Materials array is sorted by material_id to achieve deterministic serialization

### 3. RFC 8785 — JSON Canonicalization Scheme (Tue, Jun 2, 2020)
**Link:** https://www.rfc-editor.org/rfc/rfc8785

**Relevance:** Deterministic JSON serialization for cryptographic operations; directly applicable to hashing

**Key Findings:**
- Define a **canonical form** of JSON by:
  1. **Sorting object keys** lexicographically before serialization
  2. **Disallowing whitespace** except around structure delimiters
  3. **Normalizing number format** (no leading zeros, no trailing zeros in decimals, use exponential notation for very small/large numbers)
  4. Disallowing **undefined** or **NaN/Infinity**
- Two different JSON orderings produce identical canonical form and hash
- This enables **content-addressed IDs**: hash(canonicalize(json)) is deterministic

**Applied To Graphics Intent v1:**
- `canonicalizeJson()` function explicitly sorts all object keys recursively
- `canonicalStringify()` produces RFC 8785-compliant JSON before hashing
- Snapshot IDs use pattern: `gfx:scene-snap:<sha256>` where sha256 is hash of canonical JSON
- Deterministic across runs: shuffle nodes/materials, canonical form and hash remain identical

### 4. Three.js Object3D.renderOrder (Three.js Docs)
**Link:** https://threejs.org/docs/#api/en/core/Object3D.renderOrder

**Relevance:** Explicit render ordering; avoids z-fighting and depth-sorting brittleness

**Key Findings:**
- `renderOrder` is a numeric property on three.js Objects
- Renderer sorts by renderOrder **before** depth-testing
- Useful for **UI overlays**, **transparent objects**, and **order-dependent rendering**
- Default is 0; higher values render last (on top)
- Solves the problem: "I want this mesh to always render in front of that one, regardless of depth"

**Applied To Graphics Intent v1:**
- `NodeSpecV1.mesh` includes `layer: u8` and `render_order: i16` fields
- Render commands are sorted as: `(layer asc, render_order asc, node_id asc)` before being written to RenderPacket
- Renderer can directly use these values to set `object3D.renderOrder = (layer << 16) | (render_order & 0xFFFF)`

---

### 5. Three.js Discourse: renderOrder Usage & Transparency Ordering Notes
**Referenced URLs (implicit):**
- Three.js forum discussions on transparent object sorting
- Community patterns for deterministic rendering order

**Relevance:** Real-world rendering order challenges and solutions

**Key Findings:**
- **Transparency + depth sorting:** transparent objects need **back-to-front** ordering for correct blending
- **Opaque objects:** benefit from **front-to-back** ordering (early z-fail rejection)
- **Solution:** Assign explicit renderOrder to all objects; disable Three.js automatic sorting with `scene.sortObjects = false`

**Applied To Graphics Intent v1:**
- RenderPacket commands are pre-sorted with deterministic order
- Renderer can loop through commands in order and draw immediately without re-sorting

---

### 6. MDN JSON.stringify (Updated Jul 10, 2025)
**Link:** https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/JSON/stringify

**Relevance:** Clarifying JSON.stringify key ordering behavior (spoiler: not guaranteed)

**Key Findings:**
- **Object property iteration order in JavaScript is defined:**
  - Integer-like keys come first (in ascending numeric order)
  - String keys come next (in insertion order)
  - Symbol keys come last
- **JSON.stringify follows this order for object keys**
- **BUT:** this is an implementation detail; spec does NOT guarantee key order for JSON serialization
- **Conclusion:** NEVER rely on `JSON.stringify()` key order for cryptographic/deterministic hashing

**Applied To Graphics Intent v1:**
- `canonicalizeJson()` explicitly sorts keys alphabetically (`a < b ? -1 : ...`)
- Even if JavaScript engine changes key ordering, canonical form remains stable
- Defensive programming: "don't assume; sort"

## Decision + Rationale

### Why Graphics Intent → RenderPacket as Module 4?

1. **Lowest friction with existing substrate:**
   - Reuses canonical JSON + hashing (same patterns from World Core v1)
   - No new serialization algorithms needed

2. **Visual validation of determinism:**
   - Users can see identical RenderPacket hashes across runs
   - HUD display of packet hash provides immediate feedback
   - Satisfies "is it really deterministic?" skepticism

3. **Foundation for all future graphics:**
   - Scene graph contract is stable and well-understood (glTF pedigree)
   - Render command ordering is explicit and testable
   - Three.js/native/headless renderers can all interpret the same packet deterministically

4. **Low coupling, high leverage:**
   - Does NOT require Local Lexicon (DB) integration
   - Does NOT require Automation (job scheduling)
   - Integrates cleanly with existing ledger + tools system
   - Minimal risk of scope creep

5. **Ship order (recommended):**
   - **Module 4:** Graphics Intent v1 (this module)
   - **Module 5:** Three.js Renderer (interpret RenderPacket on client)
   - **Module 6:** Local Lexicon (persistent scene storage, query optimization)
   - **Module 7:** Automation (batch render jobs, timeline composition)
